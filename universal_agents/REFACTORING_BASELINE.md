## 1. Что вообще делает программа

Это автономный LLM-агент-ассистент с инструментами (чтение/правка файлов, поиск, запуск
команд, делегирование суб-агентам, планирование задач и другими). Пользователь пишет в консоль
сообщение; агент общается с локальной моделью через OpenAI-совместимый API
(LM Studio по умолчанию), вызывает инструменты, смотрит результаты, повторяет цикл, пока
задача не решена.

Главный принцип, определяющий всю архитектуру: **история диалога должна оставаться
валидной для API и при этом стоить как можно меньше токенов**. Отсюда почти всё остальное —
сжатия, пропуск повторных чтений, рабочая память, компактизация задач.

## 2. Железные правила (их нельзя нарушать)

1. **Системный промпт всегда под индексом 0, диалог начинается с 1.** Везде, где режут
   историю, нижняя граница — этот индекс. Нарушить = отрезать системный промпт.
2. **Префикс сообщений стабилен ради переиспользования KV-кэша.** Поэтому инструменты
   передаются модели даже в служебных вызовах (саммаризация и т.п.), где звать их не надо;
   заголовки пользовательских сообщений кэшируются; суб-агент наследует историю родителя.
   Нарушить = каждый вызов будет пересылать весь контекст заново и дорого стоить.
3. **Один вызов инструмента за ход — жёстко.** Это продиктовано тремя слоями сразу: промпт
   требует, API просят не параллелить, а агент при нескольких вызовах оставляет только один.
   Это сделано для повышения стабильности и уменьшения повторных вызовов.
4. **Ошибки инструментов имеют единый формат.** Результат начинается с `Error:` (или это
   помечено флагом «отклонено пользователем»). Агент узнаёт ошибку по этому признаку и решает,
   перегенерировать ли ответ. Отклонение пользователем — отдельный случай (не ошибка выполнения,
   но тоже блокирует дедуп).
5. **Любая операция над историей (удаление, сжатие, компактизация) сбрасывает кэш прочитанных
   файлов.** Потому что read-результат мог быть выброшен или переписан — и повторное чтение
   должно реально перечитать файл.
6. **Рабочая память (плотные саммари сообщений) привязана к живым объектам сообщений.**
   После любого удаления осиротевшие записи выбрасываются; при сохранении/загрузке истории
   саммари привязываются заново по позиции (объекты пересоздаются).

## 3. Поведение по сценариям

### 3.1. Один запрос пользователя — что происходит по шагам

Когда пользователь вводит текст:
- Агент добавляет сообщение в историю. Если оно очень длинное — может сразу снять с него
  короткое саммари в «рабочую память» (не в контекст). Чтобы потом не тратить отдельное время на суммаризацию, 
когда подойдёт время и порог заполнения контекста будет превышен. Саммари делается на текущей истории с указанием
маленького отрывка того сообщения, которое просим модель суммаризовать (для повышения скорости работы). 
- Готовит историю к отправке: **сначала её чинит** (см. 3.3), потом добавляет к пользовательским
  сообщениям служебные заголовки (к каждому пользовательскому сообщению время отправки и статистику сколько токенов
осталось, чтобы LLM мог следить за количеством собственной памяти).
- Зовёт модель. Если включён стриминг (сейчас это не так, но хотелось бы чтобы стримились вообще все обращения 
к API LLM, некоторые из них сейчас не логгируются и это неудобно. короче везде где возможно и 
поддерживается стриминг чтобы был) — собирает ответ по кусочкам и показывает живьём; иначе ждёт целого ответа.
- Смотрит, что вернула модель:
  - **Пусто** → выбрасывает и пробует снова.
  - Есть вызов(ы) инструмента → проверяет на повтор (3.4),
    спрашивает подтверждение если надо (3.2), выполняет, смотрит результат, при необходимости
    сжимает его (3.6).
  - Есть только текст → проверяет, не повторяет ли он предыдущий ответ дословно или с минимальными отличиями (3.4);
    если повтор — пробует с повышенной температурой генерации несколько раз (сейчас он перестаёт работать с
повышенной температурой после того как получил первый отличающийся токен, но на практике это не защищает от
 повторов так хорошо, поэтому нужно добавить порог несколько токенов
 которые будут отличаться чтобы затем снизить температуру до обычной) 
- Если модель вернула «сломанный» вызов (похоже на XML, но не распарсился) — входит в порядок
  восстановления: сначала перегенерирует с повышенной температурой, потом вливает в историю
  подсказку условно «пиши правильный формат», потом, если совсем не выходит, отдаёт управление пользователю.
- После каждого шага: если помечены завершённые задачи — сжимает их (3.5); если контекст
  забит больше порога — суммаризирует старую часть диалога (3.6).
- Цикл повторяется, пока модель не даст чистый текстовый ответ без инструментов 
(маркер того, что модель закончила работу над задачей или просит уточнение от пользователя).

### 3.2. Инструменты: подключение, безопасность, подтверждение

**Как устроен набор инструментов.** У агента внутри есть менеджер, который хранит активные
инструменты (их схемы для API + сами функции + флаги безопасности). Но логика агента разбита
на куски (миксины), и они не должны лезть внутрь менеджера напрямую. Поэтому агент выставляет
им «окна»: «дай список активных инструментов», «дай их схемы», «дай текущий конфиг»,
«дай доверенные папки». Когда, скажем, исполнитель хочет узнать, можно ли доверять пути, он
спрашивает у агента — а агент переадресует менеджеру. Зачем так: миксины пишутся независимо
и не должны зависеть от внутренностей менеджера, это для лучшего разбиения на файлы 
(но архитектура может быть пересмотрена, если существует более оптимальная).

**Загрузка инструментов «на лету».** Стартовый набор минимален (загрузчик, планировщик, 
возможно еще какие-то самые частоиспользуемые),
остальное модель открывает сама командой `load_tool`. Когда инструмент загружается, менеджер
сканирует папку плагинов и добавляет его. Важно: если появился хоть один инструмент, который
можно выгрузить, менеджер сам подцепляет и `unload_tool` (чтобы агент мог убрать то, что сам
включил). Сами `load_tool` и `unload_tool` выгрузить нельзя никогда
(иначе агент отрежет себе возможность менять набор). На текущий момент ясно, что `unload_tool`
должен срабатывать только во время изменения истории (если дать ему сработать раньше, то он разрушит KV-cache 
потому что описания инструментов шаблоном jinja хранятся в системном промпте в самом верху префикса. 
Поэтому префикс когда и так уже меняем сжатием истории - за одно можно и инструменты выгрузить лишние. А до тех пор 
инструменты к которым вызван unload_tool должны просто запоминаться чтобы выгрузить их позже.

**Безопасность путей.** Инструменты для выполнения shell команд помечены флагом «проверять пути». Перед
выполнением агент вытаскивает из команды пути (умеет разбирать кавычки, переменные окружения
`$HOME`, `%VAR%`, backtick в PowerShell), проверяет существование этих путей на диске, и смотрит, не
выходят ли они за пределы папки проекта (где `.git`). Если существуют и выходят — это внешний путь: агент
предупреждает и требует подтверждения у пользователя (чтобы ничего случайно не удалить или не изменить). 
Лучше лишний раз спросить, чем по ошибке перезаписать файл вне проекта. Правка файлов через инструмент 
`edit_file` пропускает подтверждение, если путь внутри «доверенной папки» (по умолчанию — корень git репозитория, 
потому что git позволит откатить любые правки).

**Подтверждение.** Инструмент требует подтверждения, если он либо помечен как опасный (который может модифицировать 
файлы). В доверенной папке даже опасные инструменты (shell и edit_file) подтверждение не спрашивает. Если
есть внешние пути — подтверждение для опасных инструментов требуется. Отказ пользователя превращается в
специальный результат «отклонено» и не считается ошибкой выполнения.

### 3.3. История и её авто-починка

История — это список сообщений (система, пользователь, ассистент, результат инструмента).
Сейчас перед КАЖДОЙ отправкой в модель агент её «нормализует» чтобы роли шли валидно. 
Но я понимаю, что нормализация нужна только тогда, когда в истории реально что-то меняется 
(например сжимается переписка) и её не обязательно вызывать на каждом прям шаге. 
Что делает нормализация:
- Следит за тем, чтобы самым первым сообщением всегда был системный промпт, а вторым - сообщение пользователя 
(некоторые шаблоны jinja требуют такой порядок). Если пользовательских сообщений не осталось вообще — вставляет
  заглушку-приветствие (иначе диалог без пользователя сломался бы по jinja шаблону).
- Следит за тем, чтобы после сообщений ассистента с вызовами инструментов внутри шло сообщений с ролью 
tool с результатом выполнения инструмента (для jinja и самой LLM - иначе она повторно будет пытаться вызвать инструмент).
- Результат инструмента цепляет к истории, только если он действительно отвечает вызову
  предыдущего ассистента (по id). Осиротевшие результаты (вызов удалили, а результат остался)
  выкидываются — иначе API их не примет.
- Сливает подряд идущие сообщения одного типа (два пользовательских склеиваются через пустую
  строку; два ассистента — их тексты и вызовы тоже). Зачем: чтобы шаблоны jinja правильно работали.
- Если после аварийного восстановления история кончается результатом инструмента — добавляет
  заглушку-ассистента, иначе API невалидна (не очень понял, почему шаблон jinja выдавал ошибку 
иначе, ведь по идее после результата инструмента может быть сообщение ассистента... короче это проверить надо)


**Сохранение/загрузка.** История пишется в JSON вместе со списком загруженных инструментов,
состоянием прочитанных файлов и рабочей памятью. Рабочая память привязана к живым объектам
сообщений по `id()`, который при загрузке не переживёт, поэтому при чтении саммари привязываются
заново по позиции сообщения.

### 3.4. Защита от зацикливания и дубликатов

**Два уровня проверки.** Повторяющийся вызов (одинакового инструмента с одинаковыми аргументами) удаляется 
и производится попытка перегенерации того же сообщения с повышенной температурой (в надежде что температура сдвинет 
зицикливание с мёртвой точки) на несколько попыток. На этапе исполнения инструмента обвязка агента сама проверяет: если модель зовёт тот же
инструмент с теми же аргументами в рамках текущего хода — агент возвращает ей «заблокировано,
не повторяй». Зачем дважды: если простое повышение температуры не помогло, то,
а модель должна получить явный отказ, чтобы сменить стратегию.

**Как детектор повтора смотрит назад.** Идёт от системного промпта до последнего сообщения
пользователя (всё до него — не текущий ход).

**Повтор текстового ответа.** Если модель отвечает текстом, похожим на предыдущий (меряется
по доле общих слов, Jaccard), агент считает это повтором и перегенерирует с повышением температуры > 1.

**Сломанный вызов.** Если ответ похож на нераспарсенный вызов инструмента (есть открывающий
XML-тег и имя известного инструмента рядом со скобкой) — агент ловит это до исполнения и
включает восстановление. Гейт «должен быть XML-тег» нужен, чтобы не ловить фразы вроде
«функция cwd() возвращает…».

### 3.5. Планирование задач (make_plan / have_done)

**Идея.** Для длинных задач модель сначала составляет плоский упорядоченный план
`[{id, title}, ...]`, а потом отмечает пункты выполненными строго по порядку. `have_done`
подключается к агенту автоматически только после успешного `make_plan` (до этого его нет в
наборе).

**Контроль порядка.** Когда модель вызывает `have_done`, агент проверяет цепочку условий:
- id непустой и есть в плане;
- не все пункты ещё закрыты;
- закрываемый id — именно следующий по плану (иначе «OUT-OF-ORDER, делай по порядку»);
- между последним закрытым пунктом и этим реально была работа инструментами (чтение/правка/запуск),
  иначе «NO-WORK-DONE, ты не делал задачу, а отмечаешь». Определённые вызовы
  (`make_plan`, `have_done`, `load_tool`) при этом не считаются «работой».

**Компактизация завершённых задач.** Когда пункт закрыт, его «сырой» кусок истории
(вызовы и результаты между маркерами плана) можно сжать: агент просит модель выдать плотное
саммари сегмента, и если оно короче оригинала — заменяет кусок одним сообщением. Маркеры
плана и `have_done` остаются видимыми (чтобы порядок не потерялся). Если саммари не короче —
пропускает. Раздутый результат `have_done` тоже подрезается.

### 3.6. Экономия контекста: сжатия трёх видов

**А. Рабочая память (плотные саммари сообщений).** Каждое длинное сообщение ассистента/
пользователя/результата инструмента может сразу сжиматься в короткую выжимку, которая хранится
вне контекста. При сжатии всего диалога эти выжимки склеиваются в один короткий текст. У `read`
есть особенность: его результат заменяется выжимкой прямо на месте (файл больше не висит в
памяти). Зачем вне контекста: чтобы заранее собрать саммари и не собирать его долго когда потребуется почистить контекст.

**Б. Авто-суммаризация диалога по порогу.** Когда контекст забит больше порога, агент
снимает висячие незавершённые вызовы инструментов, берёт старую часть (кроме N последних
сохраняемых в оригинальном виде сообщений) и заменяет её на короткие саммари, которые уже хранятся в памяти из пункта А.
Если сжало мало (общее количество символов уменьшилось менее чем на определенное значение) — пересборка с урезанием
длинных выводов инструментов.

**В. Сжатие сверхдлинного вывода инструмента (который не помещается в оставшийся лимит контекста модели).** Длинный 
результат инструмента нарезается на куски, каждый кусок даётся суб-агенту с заданием «вытащи важное
по цели», накопленные выжимки склеиваются. Если суб-агент говорит «цель найдена» или «мусор» —
останавливается раньше (этот режим возможно стоит доработать, но пока пусть будет таким).

### 3.7. Чтение файлов — четыре режима

Когда модель читает файл:
- **Диапазон строк** (`start_line`/`end_line`) — возвращаются только указанные строки с
  реальной нумерацией. Отрицательный конец работает как в python-срезе.
- **Маленький файл** — целиком с построчной нумерацией.
- **Большой файл без диапазона** — интерактивная выемка: сейчас это работает иначе, но я хочу, чтобы работало так: 
- при чтении большого файла просто возвращался бы 1 раз структурный скелет (повторные чтения без 
изменения контента или истории запрещены). Ещё запрещено читать более 10% строк файла за раз (либо более N 
строк за раз). Это нужно чтобы заставить модель не читать хранить в контексте ничего лишнего, соответственно не 
читать это, чтобы оно не записывалось в контекст, а вести себя примерно как человек, читать порциями когда необходимо.
- **Папка** — дерево (с датами; если вложенных много — ветка обрезается и пишется «N items,
  размер») Это сейчас сделано очень оптимально для экономии контекста тоже.

**Пропуск повтора чтения.** Агент помнит хэш содержимого каждого прочитанного файла и привязку
к результату в истории. Если модель снова читает тот же неизменённый файл, чей результат ещё
цел в истории, — агент возвращает «повторное чтение запрещено, контент уже в контексте» и
не тратит токены. (См. дефект №2 — сейчас эта защита работает не вполне корректно.)

**Поиск.** Ищет текст или регексп по файлам, с фильтрами-глобами включения/исключения,
показывает совпадения с контекстом ±1 строка, группирует смежные. Регексп определяет по
наличию спецсимволов; некорректный — возвращает ошибку. Должен лимитироваться настраиваемым количеством 
показываемых результатов и по-хорошему как и длинные выводы инструмента - иметь возможность обрабатываться интерактивно
(батчами через суб-агента, как если бы человек постепенно смотрел результаты и листал бы их от начала до конца с 
определённого размера окном на мониторе).

### 3.8. Суб-агенты

Делегирование задачи суб-агенту: создаётся изолированный агент, который наследует системный
промпт и историю родителя (для переиспользования KV-кэша), но со своим бюджетом токенов и своим
трекером (бюджет и трекер я думаю тоже можно сделать общими, смысл им отдельными быть не вижу). 
Инструменты, требующие подтверждения или проверки путей в наборе остаются, но при изменении в недоверенных путях 
происходит автоматический отказ в опасных инструментах (неинтерактивный суб-агент не должен менять ничего вне 
доверенного). Глубина вложенности ограничена (1). Суб-агент возвращает только финальный текст и вся его личная история 
ходов кроме общей части, с которой он начинал, удаляется.

### 3.9. Стриминг и «расхождение»

При стриминге ответ собирается по чанкам и показывается живьём. Есть механизм защиты от
галлюцинации: если модель при высокой «буст-температуре» начинает отвечать не тем, что было
раньше (расходится с префиксом предыдущего ответа), агент обрывает генерацию и достраивает
остаток спокойной температурой — чтобы буст не успел наплодить бреда. Я думаю тут не до первого расхождения надо обрывать, 
а дать некоторый бюджет токенов, после которого только будет вырубаться (иначе опять похожее сгенерирует).

### 3.10. Self-consistency

Альтернативный режим: модель генерирует несколько независимых черновиков, агент синтезирует
из них итоговый ответ (с аннотацией предложенных инструментов). Если в черновиках есть
вызовы инструментов — выполняет один проход и берёт финальный ответ модели без инструментов.

### 3.11. Консоль и команды

Пользователь может не только писать сообщения, но и давать слэш-команды:
- `/regen` — перегенерировать последний ответ (откатывает историю до последнего сообщения пользователя
  и заново вызывает генерацию моделью);
- `/prefill` — задать текст, с которого модель начнёт ответ;
- `/save` и `/load` — сохранить/загрузить историю вместе с инструментами, файлами и рабочей
  памятью;
- `/consistent` — вкл/выкл режим self-consistency;
- `/multiline` — ввод многострочного текста (терминатор `/mm`);
- `/trust` и `/untrust` — управление доверенными папками (в т.ч. `--clear`).

## 5. Спящие дефекты

Эти вещи «работают» только потому, что соответствующие флаги выключены или код не задействован. Думаю, что 
их заодно можно поправить!

1. **Падение при включении Responses API.** Если переключить флаг на Responses API, любой
   успешный ответ провалится с внутренней ошибкой (переменная `prefill` используется в коде, но
   не передаётся в функцию), поймается общим перехватом, вернётся как ошибка API, и агент
   молча пошлёт тот же запрос повторно через запасной путь — двойной расход. Сейчас скрыто, т.к.
   флаг выключен по умолчанию.
2. **Защита от повтора чтения не срабатывает.** Агент при исполнении проверяет, не является ли
   результат уже сжатым выемкой, по текстовым меткам — но те метки, что он ищет, не совпадают с
   теми, что реально генерирует чтение файла. Поэтому проверка никогда не срабатывает, и сжатый
   read может быть сжат повторно. Фикс — вынести метки в общие константы.
3. **Учёт потраченных токенов работает очень разрозненно насколько мне известно**. В разных местах он работает
по-разному. Нужно чтобы был унифицированный механизм, который обновлял счётчик тогда, когда пришла информация из API
и всё. Максимум он может пытаться заранее оценить сверху сколько будет потрачено токенов после отправки нового 
сообщения, по которому еще количество токенов неизвестно и для этого используется константа из Config `CHARS_PER_TOKEN`. 
Думаю, было бы неплохо для каждого сообщения сохранять где-то в отдельном поле сколько токенов оно занимает (полученную 
информацию из API, если такого еще не делается).
4. **Мёртвый параметр «системный промпт»** протянут через несколько функций суммаризации, но
   нигде не используется.
5. **Закомментированный код.** Около сотни строк старой реализации `edit_file`, закомментированный
   вызов ревью в компактизации задач, неиспользуемый импорт. Хочется как-то разделить режимы работы edit_file. Но дело 
в том, что по-умолчанию LLM приоритизирует редактирование через точную замену. Однако для больших кусков текста это 
намного медленнее работает, поэтому было принято решение сделать альтернативный путь через замену по номерам строк (
тогда модели не приходится писать old_text и это намного быстрее). Короче для больших замен быстрее и лучше делать по 
номерам строк, а для маленьких или которых много заменить разом - по точному совпадению. Пока я не придумал, как их 
разделить, чтобы модель адекватные приоритеты им давала, поэтому закомментировал путь через точную замену.
6. **Недостижимая ветка** в форматировании размера файла (если она есть, как автор говорю, что я не знаю, не проверял, 
этот пункт писал LLM).
7. **Разная защита хвоста** при ручном сжатии истории (3 сообщения) против везде elsewhere
   (1 сообщение из конфига) — мелкое расхождение стиля.
8. **Подмена трекера токенов у суб-агента после создания** вместо передачи при конструировании.
9. **Лазание в приватное поле истории** напрямую из миксина сжатия вместо публичного метода.
10. **Подготовка истории мутирует её** (вызывает починку) — 
    рефакторинге нельзя превратить в чистую функцию, не синхронизировав логику восстановления (как автор не уверен, это 
тоже писал LLM).

## 7. Чеклист базовой базы правил и установок

- Максимизация переиспользования KV-cache за счёт совпадения префикса (неизменность системного промпта, инструментов 
(кроме load_tool), истории (кроме когда пора сжимать))
- Минимизация лишней информации в контексте (огромные выводы инструментов надо как-то сжимать разными способами). Если 
какая-то информация выкидывается, то очень желательно допустимость её выкидывания из контекста должна подтвердить сама 
LLM как интеллектуальный механизм.
- Минимизация длины промптов и системных сообщений от инструментов относительно их функциональности и влияния на LLM (
копейка рубль бережёт).
