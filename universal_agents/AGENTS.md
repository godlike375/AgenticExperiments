# AGENTS.md

> Этот файл читают LLM-агенты (opencode, Cursor, Copilot) при работе с проектом.
> Следуй этим правилам — и код будет правильным с первого раза.

---

## 0. Цель проекта

Создать самую качественную обвязку (framework) вокруг LLM, которая выжмет максимум из любой модели через специальные трюки и хитрости:
- **KV-cache reuse** — стабильный префикс сообщений для максимального переиспользования кэша
- **Экономия контекстного окна** — умное сжатие, суммаризация, периферийное зрение, архивация
- **Стабильность** — защита от зацикливания, восстановление после ошибок, авто-ремонт истории

## 1. Абсолютные инварианты (нарушить = сломать)

### 1.1. Системный промпт всегда под индексом 0

Диалог начинается с индекса 1. Никогда не удалять и не перемещать системное сообщение.

### 1.2. KV-cache: стабильный префикс

Префикс сообщений (системный промпт + инструменты + начало истории) должен оставаться байт-идентичным между вызовами LLM. Нарушение = каждый вызов пересылает весь контекст заново и дорого стоит.

Отсюда вытекает:
- Инструменты всегда передаются в API даже в служебных вызовах (саммаризация и т.п.), где звать их не нужно
- Заголовки пользовательских сообщений кэшируются; инвалидация — единая точка, кэш сбрасывается только когда мутация меняет «последность» сообщения или правит его содержимое
- Суб-агент наследует системный промпт и историю родителя
- При загрузке/выгрузке инструментов через `load_tool`/`unload_tool` схемы не удаляются из префикса — `unload_tool` только помечает, реальное удаление происходит при инвалидации кэша (сжатие, удаление, правка истории)

### 1.3. Один вызов инструмента за ход

Модель может вызвать только один инструмент за сообщение. Это ограничение API и промпта. Сделано для повышения стабильности и уменьшения повторных вызовов.

### 1.4. Единый формат ошибок инструментов

Результат начинается с `Error:` (через `constants.err()`) или помечен флагом «отклонено пользователем». Агент различает ошибку и отказ по этим признакам.

### 1.5. Сброс кэша чтений при мутации истории

Любая операция над историей (удаление, сжатие, компактизация) сбрасывает кэш прочитанных файлов. Причина: результат чтения мог быть выброшен или переписан, и повторное чтение должно реально перечитать файл.

### 1.6. Два представления: `to_api_dict()` и `to_persist_dict()`

Первое — для запроса к модели. Второе — для JSON-файла (содержит внутренние флаги: `_skip_summarize`, `_is_error` и т.д.). Никогда не путать назначение.

### 1.7. Устойчивость к ошибкам модели

Пустой ответ → перегенерация. Сломанный инструментальный вызов (похож на нераспарсенный XML) → цепочка восстановления: сначала перегенерация с повышенной температурой, затем вставка подсказки формата в историю, в крайнем случае — сдача пользователю. Модель всегда должна иметь возможность выйти из тупика.

### 1.8. Автосохранение

Состояние агента автоматически сохраняется после каждого выполненного инструмента и каждого нового сообщения пользователя. Это保障а отказоустойчивости: при аварийном завершении история не теряется.

### 1.9. Детекция повторов текста и reasoning по всей истории

Для борьбы с зацикливанием (модель пишет одно и то же перед каждым вызовом инструмента или в reasoning-блоке) `_detect_duplicate` проверяет точное совпадение хэша (SHA-256) содержимого нового ответа или reasoning-блока с **любым** более ранним `AssistantMessage` из текущей истории — даже если между ними 100 итераций. Хэши считаются на лету по `self.history.get_all()` (нет отдельного хранилища — редактирование/сжатие/загрузка автоматически актуализируют набор, дрейфа состояния нет; `Config.DUPLICATE_TEXT_MIN_CHARS` управляет минимальной длиной для признания повтором, 0 = без ограничения). При совпадении срабатывает эскалация с ростом температуры и «нагами»: первые дубли (до `Config.DUPLICATE_NAG_THRESHOLD`) просто отбрасываются с бустом температуры, без каких-либо LLM-видимых сообщений; только после порога в контекст вставляется предупреждающая инструкция (NAG). Если за `MAX_LOOP_RETRIES` попыток модель так и не исправилась — дубль **не** пропускается как есть, а управление сдаётся пользователю (`_recover('duplicate_loop')`).

## 2. Архитектура

### 2.1. Миксины

`LLMAgent` формируется из семи миксинов, каждый отвечает за свою область:
- Управление инструментами
- Рабочая память и компакция диалога
- Удаление/восстановление сообщений
- Стриминг + детекция расхождений + watchdog
- Сборка ответа ассистента, обработка ответа, NO COMMENT flow
- Выполнение вызовов инструментов, подтверждение, dry_run
- Self-consistency режим (несколько черновиков + синтез)

**Принцип:** миксины обращаются к агенту через `self` неявно. Нет интерфейса/протокола — это осознанный компромисс для простоты. При добавлении нового миксина полагайся на те же поля, что и остальные: `self.history`, `self.tools_manager`, `self.token_tracker`, `self.on_system_msg`, `self.on_render`, `self.stop_event`, `self._gen_params`, `self.loop_detector`, `self.file_states`, `self.archive`.

### 2.2. Инструменты

**Паттерн создания.** Инструменты — функции в `tools/`, декорированные `@tool`. Декоратор автоматически генерирует JSON Schema из аннотаций типов. Имя инструмента = имя функции (никогда не дублировать строковым литералом). Типы параметров: `str`, `int`, `float`, `bool`, `list`, `dict`.

**Флаги безопасности:**
- `requires_confirmation` — спрашивает подтверждение у пользователя
- `requires_model_confirmation` — двухфазное подтверждение: dry_run → превью → модель отвечает `answer_to_system` → выполнение
- `path_safety` — проверяет пути вне проекта перед выполнением
- `safe_in_trusted` — в доверенной папке пропускает подтверждение пользователя

**Динамическая загрузка.** Стартовый набор инструментов минимален, остальное модель открывает сама командой `load_tool`. При появлении первого выгружаемого инструмента автоматически подключается и `unload_tool` (чтобы агент мог убрать то, что сам включил). `load_tool` и `unload_tool` выгрузить нельзя никогда — иначе агент отрежет себе возможность менять набор.

**Выгрузка без удаления.** `unload_tool` не удаляет инструмент сразу, а помечает его. Он остаётся в описании системного промпта, чтобы не ломать KV-кэш. Если модель попытается вызвать выгруженный инструмент — получит ошибку. Реальное удаление происходит только при изменении истории (сжатие, удаление, правка) — на этих точках кэш и так пересобирается.

**Безопасность путей.** Инструменты с `path_safety` вытаскивают пути из команды, проверяют их существование и смотрят, не выходят ли они за пределы папки проекта (где `.git`). Внешний путь → предупреждение и требование подтверждения. В доверенной папке (по умолчанию — корень git-репозитория) опасные инструменты подтверждение не спрашивают — git позволит откатить любые правки.

**Суб-агенты.** Наследуют системный промпт, историю и полный набор инструментов родителя (для переиспользования KV-кэша, схемы не дублируются), но со своим трекером токенов. Подтверждения для инструментов суб-агент получает автоматически (интерактивности у него нет). Опасные инструменты блокируются только в режиме `safe_only` или при явном `denied_tools` (вызов запрещённого возвращает ошибку «forbidden» — схема в префиксе остаётся). Глубина вложенности ограничена. Возвращает только финальный текст.

### 2.3. Конфигурация

`Config` в `config.py` — единый dataclass: доступ через классовые атрибуты (`Config.X`), без синглтон-экземпляра. Все настройки с дефолтами. При добавлении новой фичи — добавь константу в `Config` с понятным именем и дефолтом.

### 2.4. Производные данные — вычислять, а не хранить

Производные данные (хэши, индексы, кэши) всегда вычисляются на лету по источнику (история), а не хранятся в отдельном поле. Если источник может быть изменён через несколько путей (сжатие, загрузка, компактизация, редактирование) — хранение копии данных ведёт к рассинхронизации (drift). Вычисление на лету = нет drift-багов, нет лишних точек синхронизации. Пример: `_get_prior_text_hashes()` в `agent.py` — хэши повторов считаются по `self.history.get_all()`, а не кэшируются отдельно.

### 2.5. Эскалация стоимости при проблемах качества

При борьбе с проблемами качества (повторы, ошибки, зацикливания) — всегда эскалировать от дешёвого к дорогому:
1. Буст температуры (бесплатно, 0 токенов)
2. Предупреждение модели / NAG (стоит токенов, раздражает)
3. Сдача хода пользователю (стоп, требует интерактивности)

Не пропускать ответ как есть на шаге 3 — это превращает phantom-ошибку в реальную. Пример: `DUPLICATE_NAG_THRESHOLD` в `config.py` — NAG вставляется только после нескольких дублей подряд, а не с первого раза.

## 3. Сжатие и экономия контекста

### 3.1. Три уровня сжатия

1. **Рабочая память** (per-message summaries) — опциональный режим (`PER_MSG_SUMMARIES_ENABLED`, по умолчанию выключен; у суб-агентов есть оверрайд `disable_per_msg_summarization`). Плотные саммари длинных сообщений хранятся вне контекста (`set_per_msg_summary`). У `read` есть особенность: его результат заменяется выжимкой прямо на месте. При компакции текущий флоу использует single-shot session summary, а per-message саммари чистятся (код склейки `_build_from_per_message_summaries` есть, но в компакцию не подключён).

2. **Автосуммаризация по порогу** — когда контекст забит больше порога (по факту из API, не по оценке), старая часть (кроме N последних сообщений, сохраняемых в оригинальном виде) заменяется session summary — одним UserMessage с флагом `is_summary` в начале истории. Оригиналы перед удалением уходят в архив (см. 3.2). Неудачные/повторяющиеся саммари перегенерируются с ростом температуры; предусмотренные константы для повторного усечения выводов инструментов при слабом сжатии пока не задействованы.

3. **Сверхдлинные выводы инструментов** — `chunk_and_summarize_large_text` нарезает на чанки, каждый анализируется суб-агентом с заданием «вытащи важное по цели», результат склеивается. Если суб-агент говорит «цель найдена» или «мусор» — останавливается раньше. Механизм по умолчанию выключен (`DISABLE_TOOL_AUTO_SUMMARIZATION`) — включается константой в `Config`.

### 3.2. Archive/Recall

При компактизации оригиналы сообщений перед удалением попадают в `HistoryArchive`. Доступ через инструменты `recall_search(query)` и `recall_read(from_seq, to_seq)`.

### 3.3. Task compaction

Завершённые подзадачи (по `have_done`) сжимаются в одно summary-сообщение. Маркеры `make_plan`/`have_done` остаются видимыми, чтобы порядок не потерялся.

### 3.4. Усечение длинных выводов

Два независимых механизма. Вывод любого инструмента, не реализующего собственную обрезку, усекается до лимита `MAX_READ_CHARS_PER_CALL`: остаётся голова + маркер пропуска. Инструменты с собственной обрезкой (`read`, `search`, `run_powershell`, `run_bash_host`) обрезают сами. Выводы shell-команд (`run_powershell`, `run_bash_host`) дополнительно режутся через `truncate_middle`: голова (~40%) + хвост (~40%) + маркер пропуска.

### 3.5. Учёт токенов

Трекер собирает реальные данные от сервера LLM (`prompt_tokens`, `total_tokens`). Метод `estimate_tokens()` используется как запасной, когда данные сервера недоступны.

## 4. Добавление новой фичи — чеклист

1. Добавить константу в `Config` (если нужна настройка)
2. Реализовать в существующем модуле или создать новый в `agent_mixins/` (поведение агента) или `tools/` (инструмент)
3. Если инструмент — декорировать `@tool`, описать параметры, выставить флаги безопасности
4. Если миксин — обращаться к агенту через те же `self.*` поля что и другие миксины
5. Добавить в `PRELOADED_TOOLS` (main.py) если нужен по умолчанию
6. Добавить тест в `tests/`
7. Обновить этот файл (если изменились правила)

## 5. Стиль кода

- Язык комментариев и docstrings: **русский** (как в текущем коде)
- Имена переменных/функций/классов: **английские**
- Строки: до ~120 символов (ограничение не жёсткое)
- Типизация: `from __future__ import annotations` в каждом файле, аннотации типов обязательны
- Импорты TYPE_CHECKING: `if TYPE_CHECKING: from universal_agents.agent import LLMAgent`
- Константы: `Config` (класс) или `constants.py` (для общих маркеров)
- Формат ошибок: `constants.err(msg)` и `constants.ok(msg)` — единый формат
- Системные сообщения агенту: `ENVIRONMENT_PREFIX` ... `ENVIRONMENT_PREFIX_END`

## 6. Тесты

- Фреймворк: `pytest` (файлы `tests/test_*.py`)
- Фейковый агент: общий `make_agent` fixture в `conftest.py` (не дублировать в каждом тесте)

- Не тестировать имплементацию — тестировать поведение
- Покрытие: каждый новый инструмент/фича → тест

## 7. Чего НЕ делать

- **Не редактировать промпты и любой текст, который видит LLM** (системный промпт, `description`/`short_description`/`param`-описания инструментов, `ENVIRONMENT_PREFIX`-инструкции, наги, сообщения-ошибки для модели) без явного разрешения пользователя-разработчика. Формулировки промптов — зона ответственности человека: он экспериментирует и знает, что работает лучше. AI-агент может предложить изменение, но не применять его сам.
- **Не лезть в `self.history._messages` напрямую** из миксинов — использовать `self.history.get_all()`, `self.history.get_last_message()` и т.д.
- **Не мутировать историю без `_on_history_changed()`** — иначе кэш чтений и выгрузки инструментов не обновятся
- **Не забывать `self._needs_normalize = True`** после мутации истории (через `self.history.add()` и т.д. — уже вызывается автоматически)
- **Не добавлять `_response_id` в Streaming путь** — он только для Responses API
- **Не путать `to_api_dict()` и `to_persist_dict()`** — первый для LLM, второй для JSON
- **Не дублировать логику** между миксинами и standalone-функциями (compressors.py, task_tracker.py)
- **Не создавать новые глобальные синглтоны** — Config уже есть
- **Не менять порядок схем инструментов** — KV-кэш переиспользуется только при байт-идентичном массиве

├── agent.py              # LLMAgent — main class (composes mixins)

├── constants.py          # Shared markers (ENVIRONMENT_PREFIX, err(), ok())

├── history.py            # ChatHistory — message list with normalize/save/load
├── llm_client.py         # LLMClient — transport (chat completions, streaming)

├── task_tracker.py       # Plan + have_done + compaction
├── tool_manager.py       # ToolManager — load/unload/trust/deny

├── tool.py               # @tool decorator + JSON Schema generation

├── file_states.py        # FileStateTracker — read dedup

├── generation.py         # GenerationParams dataclass
├── command_paths.py      # Path extraction from shell commands

├── subprocess_utils.py   # Shell execution, truncation, interrupt
