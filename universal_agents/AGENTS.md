# AGENTS.md

> Этот файл читают LLM-агенты (opencode, Cursor, Copilot) при работе с проектом.
> Следуй этим правилам — и код будет правильным с первого раза.

---

## 0. Цель проекта

Создать самую качественную обвязку (framework) вокруг LLM, которая выжмет максимум из любой модели через специальные трюки и хитрости:
- **KV-cache reuse** — стабильный префикс сообщений для максимального переиспользования кэша
- **Экономия контекстного окна** — умное сжатие, суммаризация, периферийное зрение, архивация
- **Стабильность** — защита от зацикливания, восстановление после ошибок, авто-ремонт истории

## 1. Абсолютные инварианты (нарушить = сломать)

### 1.1. Системный промпт всегда под индексом 0

Диалог начинается с индекса 1. Никогда не удалять и не перемещать системное сообщение.

### 1.2. KV-cache: стабильный префикс

Префикс сообщений (системный промпт + инструменты + начало истории) должен оставаться байт-идентичным между вызовами LLM. Нарушение = каждый вызов пересылает весь контекст заново и дорого стоит.

Отсюда вытекает:
- инструменты всегда передаются в API даже в служебных вызовах (саммаризация и т.п.), где звать их не нужно
- Заголовки пользовательских сообщений кэшируются и **не пересобираются**: шапка — чистая функция от `timestamp` сообщения и от того, было ли оно последним user в момент первого обращения. Строка остатка бюджета в неё попадает только для такого сообщения и потому является снимком на момент постановки вопроса, а не текущим значением
- Правило инвалидации: пересборка — **только у сообщения, чьи собственные байта изменились** (`edit_message`, склейка соседних сообщений в `normalize`; единая точка — `UserMessage.reset_header_cache`). У изменённого сообщения KV и так мёртв, пересборка шапки бесплатна. Смена «последности» (новый вопрос, удаление хвоста, компакция, откат служебного хода, вычистка нага guard'а) шапки **не** трогает: иначе волатильная цифра бюджета сдвинула бы байты префикса, а в длинном ходе на одном user-сообщении (оно в начале префикса) — сброс стоит всего KV-кэша
- Откат служебного хода (`SERVICE_TURN_KEEP_IN_HISTORY=False`) отдельного снапшота шапки не требует: `remove_at` не трогает header-кэш уцелевших сообщений, и откат возвращает историю к байт-идентичному состоянию ([PREFIX-HASH] не возникает)
- Суб-агент наследует системный промпт и историю родителя (объекты сообщений общие — шапки тоже, инвалидация у пары не нужна)
- При загрузке/выгрузке инструментов через `load_tool`/`unload_tool` схемы не удаляются из префикса — `unload_tool` только помечает, реальное удаление происходит при инвалидации кэша (сжатие, удаление, правка истории)

### 1.3. Один вызов инструмента за ход

Модель может вызвать только один инструмент за сообщение. Это ограничение API и промпта. Сделано для повышения стабильности и уменьшения повторных вызовов.

### 1.4. Единый формат ошибок инструментов

Результат начинается с `Error:` (через `constants.err()`) или помечен флагом «отклонено пользователем». Агент различает ошибку и отказ по этим признакам.

### 1.5. Сброс кэша чтений при мутации истории

Любая операция над историей (удаление, сжатие, компактизация) сбрасывает кэш прочитанных файлов. Причина: результат чтения мог быть выброшен или переписан, и повторное чтение должно реально перечитать файл.

### 1.6. Два представления: `to_api_dict()` и `to_persist_dict()`

Первое — для запроса к модели. Второе — для JSON-файла (содержит внутренние флаги: `_skip_summarize`, `_is_error` и т.д.). Никогда не путать назначение.

### 1.7. Устойчивость к ошибкам модели

Пустой ответ → перегенерация. Сломанный инструментальный вызов (похож на нераспарсенный XML) → цепочка восстановления: сначала перегенерация с повышенной температурой, затем вставка подсказки формата в историю, в крайнем случае — сдача пользователю. Модель всегда должна иметь возможность выйти из тупика.

### 1.8. Автосохранение

Состояние агента автоматически сохраняется после каждого выполненного инструмента и каждого нового сообщения пользователя. Это保障а отказоустойчивости: при аварийном завершении история не теряется.

### 1.9. Детекция повторов текста и reasoning по всей истории

Для борьбы с зацикливанием (модель пишет одно и то же перед каждым вызовом инструмента или в reasoning-блоке) `_detect_duplicate` проверяет точное совпадение хэша (SHA-256) содержимого нового ответа или reasoning-блока с **любым** более ранним `AssistantMessage` из текущей истории — даже если между ними 100 итераций. Хэши считаются на лету по `self.history.get_all()` (нет отдельного хранилища — редактирование/сжатие/загрузка автоматически актуализируют набор, дрейфа состояния нет; `Config.DUPLICATE_TEXT_MIN_CHARS` управляет минимальной длиной для признания повтором, 0 = без ограничения). Дополнительно для текстовых ответов без tool_calls применяется биграммный Jaccard (с учётом порядка слов, в отличие от мешка слов): перестановка слов даёт низкую схожесть и не даёт ложноположительных срабатываний. При совпадении срабатывает эскалация с ростом температуры и «нагами»: первые дубли (до `Config.DUPLICATE_NAG_THRESHOLD`) просто отбрасываются с бустом температуры, без каких-либо LLM-видимых сообщений; только после порога в контекст вставляется предупреждающая инструкция (NAG). Если за `MAX_LOOP_RETRIES` попыток модель так и не исправилась — дубль **не** пропускается как есть, а управление сдаётся пользователю (`_recover('duplicate_loop')`).

### 1.10. Лимит последовательных ошибок инструментов — только одинаковых

`_recover('error_limit')` (LIMIT REACHED) срабатывает, когда **любая** сигнатура ошибки набрала `MAX_CONSECUTIVE_ERRORS` повторов за ход. Сигнатура = имя инструмента + нормализованные аргументы + SHA-256 текста ошибки (`_last_failed_tool_signature()` по истории). Счётчики ведутся **по-сигнатурно** (`TurnState.error_counts`): каждая сигнатура растёт независимо, поэтому чередование `[A,B,A,B,...]` — тоже зацикливание и прерывается, как только одна из сигнатур дошла до лимита (раньше серия «сбрасывалась» на каждой смене сигнатуры, и такой цикл шёл бесконечно). Одиночная диагностика (серия из разных сбоев, ни одна сигнатура не набрала лимит) не прерывается. Ошибка без инструмента (пустой ответ) — отдельная стабильная категория (`_NO_TOOL_ERROR_SIGNATURE`). Сбросы: успешный инструмент (`record_tool_success`) — модель продвинулась; **сжатие истории** — компакция задач или авто-суммаризация убирает старые падения из контекста, `reset_error_counts()` начинают отсчёт заново (`_compact_completed_tasks()` вернул >0 или `_auto_summarize_dialogue()` == True).

### 1.11. Guard pending-операции: приоритет над дублями, лимит срабатываний, переиспользование нага, вычистка после успеха

Пять правил защищают от «навязывания» модели неправильного пути подтверждения (инструмент с флагом `requires_model_confirmation`; см. `tools/builtin.py`):
1. **Приоритет над детектором дублей.** Пока висит pending-операция, вердикт дубля разбирает guard, а не лестница повторов. Единая точка — `_detect_duplicate`: текст без вызовов при совпадении с историей возвращает вердикт `_CONFIRMATION_GUARD_VERDICT` (вместо `answer`/`reasoning`) — `call_with_retries` по этому вердикту сбрасывает дубль, и сообщение уходит в guard; **вызов инструмента подтверждения с повторённой «пластинкой»-шапкой** возвращает `None` сразу — текст проверяется детектором дублей первым (в т.ч. для сообщений с вызовами, §1.9), и без раннего выхода правильный вызов выбрасывался бы вместе с шапкой: подтверждение не наступало никогда — модель получала `DUPLICATE ANSWER DETECTED` вместо `CONFIRM`/`CALL`, и цикл «edit → пластинка → duplicate → сдача хода» повторялся на каждом следующем вопросе пользователя. Повтор шапки при живом pending — форматирование, а не зацикливание; после снятия pending повтор снова ловится детектором.
2. **Лимит срабатываний.** Guard («ответь через инструмент подтверждения») переживает максимум `Config.ANSWER_GUARD_MAX_RETRIES` срабатываний за ход — `TurnState.can_retry_answer_guard()` декрементирует счётчик `guard_retries_left`. После исчерпания — `_recover('answer_guard')` и сдача хода пользователю (`return ""`). Прежний безусловный `continue` превращал упорную текстовую болтовку модели в бесконечный цикл до `max_iter`.
3. **Видимость для пользователя.** Каждое срабатывание guard'а печатает в консоль сообщение с честным номером попытки: `⏳ [CONFIRMATION PENDING] … (attempt N из Config.ANSWER_GUARD_MAX_RETRIES)` для N = 1..5. Сдающее ход срабатывание (6-е, когда `can_retry_answer_guard()` вернул False) не нумеруется — его закрывает `_recover('answer_guard')` со своим сообщением о сдаче. Прежний одноразовый notice (`take_guard_notice`/`guard_notice_shown`) прятал регенерации 2..5, и на 60k контекста тишина была неотличима от зависания. LLM-видимый текст при этом не меняется (наг прежний, §1.11.4).
4. **Один объект нага.** Наг создаётся один раз (`self._guard_nag_message`) и переиспользуется: `_ensure_guard_nag` при повторных срабатываниях не удаляет и не пересоздаёт его (только добавляет, если его нет). Содержимое байт-идентично между вызовами LLM, собственные байта нага не меняются — шапка не пересобирается, KV-префикс стабилен (прежний `_drop_guard_nags`, удалявший наг и плодивший новый `UserMessage` со свежим `datetime.now()`, давал ложный `[PREFIX-HASH]`). Наг помечен внутренним флагом `UserMessage._is_guard_nag` (переносится через `to_persist_dict`/`load_from_payload`), по которому `_scrub_confirmation_trail` находит его — без строкового матчинга по тексту (ToolResult-превью edit'а содержит похожую прозу).
5. **Вычистка после успеха.** Как только инструмент подтверждения вернул успех, `_scrub_confirmation_trail()` удаляет из истории все наги и «мусор подтверждения», помеченный `_mark_confirmation_junk` (текстовые ответы вместо вызова, вызовы чужих инструментов при висящем pending, упавшие пары answer). В LLM-контексте остаётся только правильный путь: превью → инструмент подтверждения → результат. Мусор хранится в `self._confirmation_junk` (словарь `id(obj) → obj`: Message unhashable, поэтому не WeakSet; сильная ссылка защищает id от переиспользования → identity-проверка в скрабе не срабатывает ложно). Пометка — в `_process_llm_response`, со снимком `pending_before` ДО `_execute_tools`: edit-инструмент сам ставит pending из dry_run внутри `_execute_tools`, и его превью-результат не должен попадать в мусор. Скраб не трогает header-кэш уцелевших сообщений: наг и мусор — временная вставка, собственные байта соседей не менялись, поэтому шапка не пересобирается и `[PREFIX-HASH]` не возникает (раньше для этого в скрабе был snapshot/restore шапки — он не нужен, раз инвалидация привязана к мутации байт, §1.2).

### 1.12. Прерываемость транспорта: остановка не ждёт сетевого таймаута

`Ctrl+C`/команда `Stop requested` обязана возвращать управление сразу, а не через `Config.TIMEOUT`. У транспорта один путь — стриминг (`StreamSession`), `LLMClient.call` всегда стримит (прежних `_run_interruptible`/`_ABANDONED`/`_call_chat_completions` нет; `Config.STREAM_ENABLED` остался только на уровне агента — `_call_with_streaming` vs `call`):
- **Транспорт** — `StreamSession` всегда открывает сырой стрим через `LLMClient.open_stream`, а тот безусловно возвращает `InProcessStream`: прямой httpx POST с `stream=True`, SSE-парсинг руками. Отмена — `close()` делает `shutdown(SHUT_RDWR)` на сокете (достаётся из `response.extensions["network_stream"].get_extra_info("socket")`), что гарантированно будит блокирующий `recv` (`close()` не будит, POSIX оставляет undefined). Работает и для TLS. Если сокет не достался (старый httpx, кастомный transport) — `close()` + read timeout как страховка. `stop_markers` обрезают контент на маркере, флаг `stopped_at_marker` вешается на результат. Если `stop_check` уже установлен до вызова, вызов не начинается вовсе (`return None, "stopped", None`).
- **Watchdog** — пока `recv` заблокирован, `__next__` не проверит `stop_check`, поэтому watchdog-поток обязателен: стартует ДО первого чанка, при срабатывании `stop_check` зовёт `LLMClient.close_stream` → `shutdown` разблокирует `recv` с `httpx.ReadError`, `__next__` видит `_closed` и возвращает `StopIteration`.
- **Таймауты httpx** — `httpx.Timeout(connect=10, read=Config.TIMEOUT, write=30, pool=10)`. `read` — пауза между байтами, не весь стрим. Если shutdown не сработал (экзотический прокси), `recv` упадёт по таймауту, а не повиснет вечно.
- **UI** — после выхода из монитора `_call_chat` джойнит поток генерации (`gen.join()`) без ограничения: отсоединения нет (фонового зомби не остаётся). Транспортный `InProcessStream` по `stop_check` закрывает соединение через `shutdown` за ~50 мс, поэтому после остановки поток завершается быстро; поток, застрявший в неинтерраптируемом инструменте, приходится переждать (выход из CLI — `Ctrl+C`).

### 1.13. Изоляция инструментов: живой ввод гарантирован убиваемыми воркерами

Ни один инструмент не может заморозить CLI: всё, что способно надолго заблокироваться (оболочка, экран/мышь, песочница, файловый ввод-вывод), исполняется в отдельном **воркер-процессе группы** (`docs/TOOL_ISOLATION_SPEC.md`). Инварианты:
- **Группа — единица изоляции.** Метка `group=` в `@tool` (домен общего состояния); инструменты одной группы живут в одном воркер-процессе. Хост не знает имён групп — набор собирается из метаданных (`tool_registry.build_tool_dict`). Внешний инструмент = нет параметра `agent` и группа ≠ `internal` (`is_external`).
- **Состояние — у хоста.** `GroupManager` владеет сессиями групп (`tool_session` — contextvar); воркер со `worker_main(group)` ничего не хранит между вызовами: состояние приходит и уходит с каждым запросом. Рабочая папка (`workspace`), масштаб экрана (`desktop`), контейнер (`sandbox`) — поля сессии, а не модульные глобалы.
- **Убиваемость.** Хост ждёт ответ, опрашивая очередь и проверяя `stop_check`; при стопе/таймауте воркер принудительно завершается (со всем деревом процессов оболочки — Windows Job Object), а следующий вызов поднимает новый. Частичный вывод команды при остановке теряется осознанно.
- **Протокол — в хосте.** Подтверждения, path-safety, усечение, загрузка/выгрузка — забота хоста; воркер исполняет только тело. Обёрнутые инструменты (`requires_model_confirmation`): dry_run и применение — в воркере, а превью → `respond_to_system` → применение ведёт хост (`make_worker_resolve`).
- **Гибридный `read`** — инструмент внутренний (учёт файлов, скелет через LLM), а низкоуровневое чтение идёт скрытым инструментом `_read_file_raw` в воркере `workspace`.
- **Плагины** — отдельная группа `plugin` с прокси-агентом (`plugin_proxy`): произвольный код изолирован, доступ к агенту — только через явный allow-list по межпроцессному каналу.
- **Тесты** — autouse-фикстура `in_process_tool_isolation` выключает изоляцию (`Config.TOOL_ISOLATION_ENABLED=False`), поэтому поведенческие тесты идут в процессе и видят моки; изоляцию проверяет `tests/test_tool_isolation.py` (явный `GroupManager(isolated=True)`).

## 2. Архитектура

### 2.1. Миксины

`LLMAgent` формируется из семи миксинов, каждый отвечает за свою область:
- Управление инструментами
- Рабочая память и компакция диалога
- Удаление/восстановление сообщений
- Стриминг + детекция расхождений + watchdog
- Сборка ответа ассистента, обработка ответа, NO COMMENT flow
- Выполнение вызовов инструментов, подтверждение, dry_run
- Self-consistency режим (несколько черновиков + синтез)

**Принцип:** миксины обращаются к агенту через `self` неявно. Нет интерфейса/протокола — это осознанный компромисс для простоты. При добавлении нового миксина полагайся на те же поля, что и остальные: `self.history`, `self.tools_manager`, `self.token_tracker`, `self.on_system_msg`, `self.on_render`, `self.stop_event`, `self._gen_params`, `self.loop_detector`, `self.file_states`, `self.archive`.

### 2.2. инструменты

**Паттерн создания.** инструменты — функции в `tools/`, декорированные `@tool`. Декоратор автоматически генерирует JSON Schema из аннотаций типов. Имя инструмента = имя функции (никогда не дублировать строковым литералом). Типы параметров: `str`, `int`, `float`, `bool`, `list`, `dict`.

**Флаги безопасности:**
- `requires_confirmation` — спрашивает подтверждение у пользователя
- `requires_model_confirmation` — двухфазное подтверждение: dry_run → превью → модель отвечает через инструмент подтверждения (см. `tools/builtin.py`) → выполнение
- `path_safety` — проверяет пути вне проекта перед выполнением
- `safe_in_trusted` — в доверенной папке пропускает подтверждение пользователя

**Динамическая загрузка.** Стартовый набор инструментов минимален, остальное модель открывает сама командой `load_tool`. При появлении первого выгружаемого инструмента автоматически подключается и `unload_tool` (чтобы агент мог убрать то, что сам включил). `load_tool` и `unload_tool` выгрузить нельзя никогда — иначе агент отрежет себе возможность менять набор.

**Выгрузка без удаления.** `unload_tool` не удаляет инструмент сразу, а помечает его. Он остаётся в описании системного промпта, чтобы не ломать KV-кэш. Если модель попытается вызвать выгруженный инструмент — получит ошибку. Реальное удаление происходит только при изменении истории (сжатие, удаление, правка) — на этих точках кэш и так пересобирается.

**Безопасность путей.** инструменты с `path_safety` вытаскивают пути из команды, проверяют их существование и смотрят, не выходят ли они за пределы папки проекта (где `.git`). Внешний путь → предупреждение и требование подтверждения. В доверенной папке (по умолчанию — корень git-репозитория) опасные инструменты подтверждение не спрашивают — git позволит откатить любые правки.

**Суб-агенты.** Наследуют системный промпт, историю и полный набор инструментов родителя (для переиспользования KV-кэша, схемы не дублируются), но со своим трекером токенов. Подтверждения для инструментов суб-агент получает автоматически (интерактивности у него нет). Опасные инструменты блокируются только в режиме `safe_only` или при явном `denied_tools` (вызов запрещённого возвращает ошибку «forbidden» — схема в префиксе остаётся). Глубина вложенности ограничена. Возвращает только финальный текст. Суб-агент переиспользует `group_manager` родителя (общие воркеры и сессии групп — §1.13).

**Группы и изоляция (§1.13).** `@tool(group=..., hidden=...)` задаёт домен состояния. Внешний инструмент (нет `agent` и группа ≠ `internal`) исполняется в воркере группы; `hidden=True` — низкоуровневый инструмент, скрытый от модели (нет в схемах/`load_tool`). Мягкий контроль разметки: инструмент без `agent` в группе `internal` даёт предупреждение при сборке `ToolManager`. Модульные глобалы доменов переселены в сессии: `workspace` — рабочая папка (`cwd`), `desktop` — масштаб экрана, `sandbox` — контейнер. `Config.TOOL_ISOLATION_ENABLED=False` возвращает исполнение в процесс хоста (тесты).

### 2.3. Конфигурация

`Config` в `config.py` — единый dataclass: доступ через классовые атрибуты (`Config.X`), без синглтон-экземпляра. Все настройки с дефолтами. При добавлении новой фичи — добавь константу в `Config` с понятным именем и дефолтом.

### 2.4. Служебный вызов LLM = один ход (`service_llm_call`)

Сервисная генерация (саммаризация, компакция, chunk-анализ, consistency-драфты) — это **один обычный ход** ассистента против той же истории: промпт добавляется в историю как `UserMessage`, дальше работает общий `_run_turn_loop` (KV-cache переиспользуется, поведение задаётся промптом сервисного вызова). Контракт:
- инструменты в служебном ходе **не исполняются** (`allow_tools=False` в `_process_llm_response`): есть текст → остаётся только текст; текста нет (голый tool_call) → перегенерация через NO COMMENT / error-механику.
- Авто-сейв (`_autosave`), компакция задач (`_compact_completed_tasks`) и авто-суммаризация **отключены** (флаг `service_mode` в `_run_turn_loop`; per-message суммаризация гейтится `_in_service_turn`).
- После завершения промпт (и ответ) либо **остаются** в истории, либо **откатываются** — настройка `Config.SERVICE_TURN_KEEP_IN_HISTORY` (дефолт False). Откат = снапшот длины истории ДО хода (`start_len`) + `history.remove_at` + `normalize` + `_on_history_changed`.
- Промпт не дублируется: `service_llm_call` сравнивает последний user-контент из `msgs` (со срезанной системной шапкой) с последним user-сообщением истории; если совпадает — `append_prompt=False` (кейс consistency-драфтов).
- Служебный ответ стримится в отдельный канал (`on_service_stream_*`), а не в основной поток, и `stop_check` агента прокидывается дальше (прерываемость компакции).
- Возврат `(msg_obj, err, usage)`: `usage=None` (токены уже учтены движком хода); `msg_obj` — `SimpleNamespace(content=..., tool_calls=[])`; для контроллерного режима итог — `controller.document()`. Вызывающие (compressors, fs, consistency) продолжают строить `msgs = история + [промпт]` — совместимо.

### 2.5. Производные данные — вычислять, а не хранить

Производные данные (хэши, индексы, кэши) всегда вычисляются на лету по источнику (история), а не хранятся в отдельном поле. Если источник может быть изменён через несколько путей (сжатие, загрузка, компактизация, редактирование) — хранение копии данных ведёт к рассинхронизации (drift). Вычисление на лету = нет drift-багов, нет лишних точек синхронизации. Пример: `_get_prior_text_hashes()` в `agent.py` — хэши повторов считаются по `self.history.get_all()`, а не кэшируются отдельно.

### 2.6. Эскалация стоимости при проблемах качества

При борьбе с проблемами качества (повторы, ошибки, зацикливания) — всегда эскалировать от дешёвого к дорогому:
1. Буст температуры (бесплатно, 0 токенов)
2. Предупреждение модели / NAG (стоит токенов, раздражает)
3. Сдача хода пользователю (стоп, требует интерактивности)

Не пропускать ответ как есть на шаге 3 — это превращает phantom-ошибку в реальную. Пример: `DUPLICATE_NAG_THRESHOLD` в `config.py` — NAG вставляется только после нескольких дублей подряд, а не с первого раза.

### 2.7. Структурированный вывод: контроллеры (`controllers.py`)

`StructuredOutputConfig` (generation.py) задаёт формат ответа LLM двумя способами:
- `from_prefill(prefill, ...)` — простая цепочка: prefill + stop-маркеры (авто извлекаются из opening-тега). Для кейсов, где полная схема не нужна.
- `from_controller(controller, ...)` — полный контроль по схеме: `XMLStructureController` парсит XML-подобную схему (`<root><a/></root>`) в пофазовые токены DFS. Подходит для всего, что заворачивается в «тег + контент» (суммаризация, chunk-анализ, file skeleton).

Контракт контроллерного хода:
- `initial_prefill()` — открывающий тег корня (+ `prefill_suffix`: произвольный текст сразу после тега, напр. `"\nL"` для file skeleton; на сравнение с токенами не влияет).
- `markers()` — закрывающие теги всех тегов схемы: любой неожиданный закрывающий останавливает генерацию фазы.
- `advance(content)` сверяет фазу с ожидаемым токеном; при несоответствии «стирает» ошибку и возвращает ожидаемый токен как `next_prefill` следующей фазы.
- **Автозакрытие при досрочном завершении:** если модель закончила ответ, не закрыв теги, контроллер сам дописывает все подряд идущие закрывающие токены (`</...>`): дошли до конца схемы → `complete=True`; остались незаполненные дети (opening-токены) → следующий opening становится `next_prefill`, генерация продолжается следующей фазой. Модель не обязана закрывать корень — контроллер дозакроет.
- Итог фазы — `ControllerVerdict(corrected_content, next_prefill, complete)`; полный документ — `controller.document()`.
- `expect_tokens(text)` — сдвиг курсора по тегам, которые вписаны за модель (в симуляции reasoning — закрывающий тег, когда модель написала мусор вместо закрывающего). Без автозакрытия: `advance()` трактует пустую фазу как досрочное завершение шаблона; несовпадение — игнорируется без побочного эффекта, задача разбирает advance().
- Сестри-соседи без обёртки-корня: `XMLStructureController.from_sibling_schema('<a/><b/>')` (`from_schema_text` множественных корней точно отказывает `ValueError`), ответ начинается с первой секции без обёртки — связка стафей для симуляции reasoning (§2.8).

Использование: `_summarize_file` в `tools/fs.py` — контроллер со схемой `<content_structure/>` (+ суффикс `"\nL"`) или `<content_structure_lines/>` (SKELETON_RANGES_MODE), `max_phases=1`. В контроллерном ходе BROKEN CALL-детекция выключена (`skip_broken_detection`).

### 2.8. Симуляция reasoning при выключенном thinking (`SIMULATED_REASONING_*`)

Пока `reasoning_effort == 'none'` (режим по умолчанию, `/think_off`), ответ обязан начаться с секции рассуждения, а всё, что после её закрытия, — свободный ответ **без тегов**. Имена открывающего/закрывающего тегов берутся из `Config.SIMULATED_REASONING_TAGS` (единственный источник истины: оттуда же и складка `sim_schema_text()` для заметок UI).

Механизм (`agent.py:_run_turn_loop` + `SimReasoningGroup` в `response_mixin.py`) — ОДИН вызов LLM на сообщение:
- Prefill открывает секцию (первый тег из `Config.SIMULATED_REASONING_TAGS`), **стоп-маркеров нет**: если модель закрыла секцию сама, мы не режем её хвост и даём дописать ответ в том же вызове (иначе пришлось бы выбрасывать уже написанный ответ и жечь лишний запрос).
- Второй тег не нужен: пустой ответ не является нарушением формата (модель вправе сразу уйти в инструмент), а лишний закрывающий тег путал модель и стоил вызова.
- Незакрытая секция закрывается нами (`close_section()`), хвост автозакрытия уходит в живой вывод (`group.appended`) — иначе в консоли тег выглядел бы незакрытым, хотя в истории закрыт.
- После закрытия всегда идёт перевод строки (`close_section()` дописывает `\n`, если его нет): ответ начинается с новой строки и в выводе, и в истории. Эхо одноразовое (`take_appended()`), иначе автозакрытие в think-фазе дублировалось бы в фазе answer; висячий `\n` при пустом ответе срезается нормализацией контента (`content.strip()` в `_process_llm_response`) — за тегом всё равно ничего нет.
- Ответ проверяется до `_process_llm_response`: нарушение формата в историю не попадает, инструменты не исполняются.
- **Пустой ответ без tool call** — единственный повод для дополнительного вызова: к концу секции подставляется `_NO_COMMENT_PREFILL` (общий механизм NO COMMENT), бюджет `Config.SIMULATED_REASONING_REPAIRS`. Приставка — наш служебный prefill, поэтому её оффсеты запоминаются (`_injected`) и вырезаются из ответа (`answer_text()`) и из контента истории (`final_content()`): иначе «ответ, на который модель ничего не написала» выглядел бы непустым и бюджет никогда не исчерпался бы. По исчерпании бюджета — ответ принимается как есть + громкий system msg.
- Пустой ответ **с** tool call принимается как есть: продолжение тут только зациклило бы ход.
- **Отдельные настройки размышлений** (`Config.SIMULATED_REASONING_TEMP/TOP_P/MIN_P/FREQUENCY_PENALTY/PRESENCE_PENALTY`, `None` = наследовать обычные): если задана хотя бы одна — двухфазный режим. Фаза think: prefill — открывающий тег секции, стоп-маркер — закрывающий (имена из `Config.SIMULATED_REASONING_TAGS`), параметры размышлений (`group.think_params()` поверх базовых хода); фаза answer: prefill — накопленное, маркеров нет, обычные параметры (`gen_params` в `call_with_retries`). Инструмент или уже дописанный ответ прямо из think-фазы принимаются как есть, без лишнего вызова; пустой ответ чинится NO COMMENT в фазе answer, как обычно. Без настроек — прежний один вызов.
- Новый вызов после инструмента начинает структуру заново (`reset()`); накопленный контент служит prefill продолжения, поэтому транспорт показывает только хвост после `prefill_shown` (уже выведенный контент не дублируется, а новая приставка видна) и не переоткрывает `on_stream_start`. Аккумулятор стрима дополнительно распознаёт повтор prefill в первых дельтах: сырой llama.cpp может вернуть его, а LM Studio — нет; в обоих случаях prefill показывается ровно один раз. Блок вывода закрывает агент (`defer_stream_end=True` в `_call_llm`/`_call_with_streaming`, закрытие в `_close_sim_stream()`), а не транспорт вызова.
- BROKEN CALL-детекция сканирует только свободный ответ — хвост после закрывающего тега (`broken_scan_text` в `_process_llm_response`), поэтому базовый гейт «есть XML-тег» снимается (`require_tag=False`). Критично: гейт выполняется по переданному тексту, а не по всему контенту — иначе теги секции рассуждения открывали бы его на каждом ответе и проза вида «read() выполнен» / «Вызываю read() для просмотра…» давала бы ложные `[BROKEN CALL]` на каждом нормальном ответе. Без гейта ловится только заведомо сломанный синтаксис — когда вызов занимает ВЕСЬ ответ (`_is_standalone_call`), плюс теги внутри ответа.
- Отключается при включённом thinking (`/think_on`, `/think`), в служебных ходах (`service_mode`), при чужом `structured_output`, пользовательском `prefill` и у субагентов.

## 3. Сжатие и экономия контекста

### 3.1. Три уровня сжатия

1. **Рабочая память** (per-message summaries) — опциональный режим (`PER_MSG_SUMMARIES_ENABLED`, по умолчанию выключен; у суб-агентов есть оверрайд `disable_per_msg_summarization`). Плотные саммари длинных сообщений хранятся вне контекста (`set_per_msg_summary`). У `read` есть особенность: его результат заменяется выжимкой прямо на месте. При компакции текущий флоу использует single-shot session summary, а per-message саммари чистятся (код склейки `_build_from_per_message_summaries` есть, но в компакцию не подключён).

2. **Автосуммаризация по порогу** — когда контекст забит больше порога (по факту из API, не по оценке), старая часть (кроме N последних сообщений, сохраняемых в оригинальном виде) заменяется session summary — одним UserMessage с флагом `is_summary` в начале истории. Оригиналы перед удалением уходят в архив (см. 3.2). Неудачные/повторяющиеся саммари перегенерируются с ростом температуры; предусмотренные константы для повторного усечения выводов инструментов при слабом сжатии пока не задействованы.

3. **Сверхдлинные выводы инструментов** — `chunk_and_summarize_large_text` нарезает на чанки, каждый анализируется суб-агентом с заданием «вытащи важное по цели», результат склеивается. Если суб-агент говорит «цель найдена» или «мусор» — останавливается раньше. Механизм по умолчанию выключен (`DISABLE_TOOL_AUTO_SUMMARIZATION`) — включается константой в `Config`.

### 3.2. Archive/Recall

При компактизации оригиналы сообщений перед удалением попадают в `HistoryArchive`. Доступ через инструменты `recall_search(query)` и `recall_read(from_seq, to_seq)`.

### 3.3. Task compaction

Завершённые подзадачи (по `have_done`) сжимаются в одно summary-сообщение. Маркеры `make_plan`/`have_done` остаются видимыми, чтобы порядок не потерялся.

### 3.4. Усечение длинных выводов

Два независимых механизма. Вывод любого инструмента без флага `self_truncating` (см. `@tool`) усекается до лимита `MAX_READ_CHARS_PER_CALL`: остаётся голова + маркер пропуска. инструменты с `self_truncating=True` обрезают сами. Выводы shell-команд (помечены `self_truncating`) дополнительно режутся через `truncate_middle`: голова (~40%) + хвост (~40%) + маркер пропуска.

### 3.5. Учёт токенов

Трекер собирает реальные данные от сервера LLM (`prompt_tokens`, `total_tokens`). Метод `estimate_tokens()` используется как запасной, когда данные сервера недоступны.

## 5. Стиль кода и общие правила
- Интерпретатором python, особенно для тестов, пользуйся только из .venv потому что там установлены зависимости (или установи если не хватает)
- Запрещены комментарии и докстринги кроме тех без которых невозможно понять важные вещи только по коду 
- Язык комментариев и docstrings: **русский** (как в текущем коде)
- Имена переменных/функций/классов: **английские**
- Строки: до ~120 символов (ограничение не жёсткое)
- типизация: `from __future__ import annotations` в каждом файле, аннотации типов обязательны
- Импорты TYPE_CHECKING: `if TYPE_CHECKING: from universal_agents.agent import LLMAgent`
- Константы: `Config` (класс) или `constants.py` (для общих маркеров)
- Формат ошибок: `constants.err(msg)` и `constants.ok(msg)` — единый формат
- Системные сообщения агенту: `ENVIRONMENT_PREFIX` ... `ENVIRONMENT_PREFIX_END`

## 6. Тесты

- Фреймворк: `pytest` (файлы `tests/test_*.py`)
- структура тестов зеркалит исходники: `agent.py → tests/test_agent.py`, `agent_mixins/foo.py → tests/agent_mixins/test_foo.py`, `tools/foo.py → tests/tools/test_foo.py`
- Средний уровень: один файл на модуль, классы — по пользовательскому поведению; не плодить файлы под каждую мелкую ветку и не писать сквозные мегасценарии через весь цикл
- Маленький модуль — маленький файл, и это нормально (`rendering`, `tool`, `context_builder`): укрупнять только слиянием с модулем-владельцем (`archive → history`, `main.allow-list → tool`, `sub_agent.permissions → tool_manager`), а не ради размера
- покрытие поведения — один раз на слой: чистый unit в файле модуля, интеграционный путь — в файле владельца поведения; точные дубли удалять, перекрывающиеся слои unit/контракт/путь сохранять
- Общие фейки/фабрики — только в `conftest.py`; локальные дубли удалять
- KV-cache и байтовые контракты префикса никогда не удалять; переносить вместе с причинным поведением
- Исключения: кросс-модульные контракты (`service_turn`, `path_safety`) могут оставаться отдельными файлами
- Фейковый агент: общий `make_agent` fixture в `conftest.py` (не дублировать в каждом тесте)
- Моки: `unittest.mock` для `on_render`, `on_confirm`, `on_system_msg`
- Не тестировать имплементацию — тестировать поведение
- покрытие: каждый новый инструмент/фича → тест
- Фичи, навязывающие формат ответа (симуляция reasoning), в тестах по умолчанию выключены autouse-фикстурой `sim_reasoning_off` в `conftest.py` — иначе фейки с «голым» текстом трактуются как нарушение формата. Тесты, которым формат нужен, включают его обратно через `monkeypatch.setattr`

## 7. Чего НЕ делать

- **Не редактировать промпты и любой текст, который видит LLM** (системный промпт, `description`/`short_description`/`param`-описания инструментов, `ENVIRONMENT_PREFIX`-инструкции, наги, сообщения-ошибки для модели) без явного разрешения пользователя-разработчика. Формулировки промптов — зона ответственности человека: он экспериментирует и знает, что работает лучше. AI-агент может предложить изменение, но не применять его сам.
- **Не лезть в `self.history._messages` напрямую** из миксинов — использовать `self.history.get_all()`, `self.history.get_last_message()` и т.д.
- **Не мутировать историю без `_on_history_changed()`** — иначе кэш чтений и выгрузки инструментов не обновятся
- **Не забывать `self._needs_normalize = True`** после мутации истории (через `self.history.add()` и т.д. — уже вызывается автоматически)
- **Не добавлять `_response_id` в Streaming путь** — он только для Responses API
- **Не путать `to_api_dict()` и `to_persist_dict()`** — первый для LLM, второй для JSON
- **Не дублировать логику** между миксинами и standalone-функциями (compressors.py, task_tracker.py)
- **Не создавать новые глобальные синглтоны** — Config уже есть
- **Не менять порядок схем инструментов** — KV-кэш переиспользуется только при байт-идентичном массиве
- **Не определять сущности по содержимому строк** (матчинг текста: маркеры, наги, типы сообщений), когда есть структурный признак — внутренний флаг (`_is_guard_nag`, `is_summary`), identity-проверка, имя инструмента/файла. Текст может повторяться в прозе ToolResult-превью и переформулироваться, давая ложные срабатывания/пропуски.
- **Не хардкодить имена инструментов строками** — использовать `tool.__name__` (и аналогично для других сущностей: теги из `Config.SIMULATED_REASONING_TAGS`, а не `"<short_think>"`). Иначе переименование инструмента молча ломает тесты.

## 9. инструменты качества кода

В репозитории установлены инструменты для поддержания качества кода:
- ruff — самый быстрый: линтер + форматтер. Проверяет стиль, F401 (unused imports), F841 (unused vars), простые баги.

- vulture — поиск мёртвого кода
